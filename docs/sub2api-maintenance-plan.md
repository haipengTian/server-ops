状态：基础维护与部署文件已实现，具体二开功能尚未确定。域名为 `proxy.thpvip.xyz`，服务器操作由用户自行通过 SSH 执行。官方 remote 已配置；GitHub 连接已恢复，本地已同步到实际核实的官方 main。尚未发布镜像或部署服务器。操作入口见 `../sub2api/README.md`。

建立可重复执行的流程：开发二开功能 → 同步并融合上游 → 验证 → 构建自己的镜像 → 部署 → 验收，后续更新沿用同一流程。

| 仓库 | 职责 |
| --- | --- |
| `haipengTian/sub2api` | 产品代码、二开功能、上游融合、测试和镜像构建 |
| `haipengTian/server-ops` | 服务器部署配置、nginx、备份、升级和回滚 |
| `Wei-Shaw/sub2api` | 官方上游代码来源 |

服务器运行个人仓库构建的镜像。生产环境通过明确的版本或镜像摘要选择发布产物，不跟随 `latest` 自动变化。

## 3. 分支与上游融合

### 3.1 推荐组织方式

- `origin/main`：个人项目已融合、可交付的代码，后续承载二开功能。
- `upstream/main`：官方远程跟踪引用，用于比较和选择同步目标。
- `codex/feature-<名称>`：每项二开功能的开发分支。
- `codex/sync-upstream-<版本>`：每次上游融合的临时分支，从个人 `main` 创建。

初始化时先检查并更新个人远程引用，再将干净的本地 `main` 快进到个人远程；如果双方已分叉，应先检查各自提交，不强制覆盖。随后配置官方 `upstream`。

### 3.2 每次同步流程

1. 获取官方分支和版本信息，优先选择明确的稳定版本；需要某项尚未发布的修复时记录具体提交。
2. 记录本次个人基线、官方目标 SHA、目标版本和关联迁移。
3. 在同步分支中 merge 官方目标，保留二开提交历史。
4. 处理冲突后检查行为：接口契约、字段、权限、前端调用、模型路由和计费都需要核对。
5. 运行现有检查及二开功能回归，通过后合入个人 `main`。
6. 创建个人发布版本，构建并部署对应镜像。

共享主分支通过 merge 保留历史。避免用强制重置、强制推送或整体替换代码的方式处理上游更新。

初期按明确请求发起同步。发现上游新版本与部署新版本是两个独立动作，未来如增加自动同步，应先生成融合分支/PR和验证结果。

### 3.3 控制长期维护成本

- 二开提交按功能拆分，避免同时格式化、改名和修改业务行为。
- 优先利用已有配置、主题、组件、服务接口和插件扩展点。
- 上游修复和二开功能分别记录，便于定位冲突和撤销单项变更。
- 在产品仓库增加 `docs/custom/`，记录二开需求、改动入口和升级回归场景。

## 4. 镜像与版本追踪

建议先复用 `.github/workflows/release.yml`，减少独立维护第二套完整构建流程。

- 镜像仓库：`ghcr.io/haipengtian/sub2api`。
- 版本命名示例：`v0.2.15-custom.1`，镜像标签对应 `0.2.15-custom.1`；示例不代表已发布或已选择首次部署版本。
- 部署优先记录 `ghcr.io/haipengtian/sub2api@sha256:<摘要>`，确保同一版本对应固定内容。
- 发布记录包含：官方基线版本与 SHA、个人代码 SHA、二开序号、镜像摘要、验证结果和迁移说明。
- 服务器为 amd64 时可选简化发布；为 arm64 时采用完整发布或增加相应构建目标。
- Fork 的 Actions 是否启用、GHCR 包是否可见、流水线是否可推送包，需要在首次发布前核实。

现有发布流程会更新个人默认分支的 `backend/cmd/server/VERSION`，并生成 `latest` 等浮动镜像标签。上游同步时应保留个人版本策略，服务器仍使用固定版本或摘要。

## 5. 服务器部署布局

延续 `server-ops` 现有约定：

| 内容 | 建议位置/方式 |
| --- | --- |
| 部署配置 | `/opt/server-ops/sub2api/` |
| 应用持久化数据 | `/opt/sub2api/app/` |
| PostgreSQL 数据 | `/opt/sub2api/postgres/` |
| Redis 数据 | `/opt/sub2api/redis/` |
| 备份 | `/opt/sub2api/backups/`，另建立异机副本 |
| 对外入口 | 主机 nginx 提供 HTTPS |
| 应用端口 | 仅绑定 `127.0.0.1:8088`（可在本地配置调整） |
| 数据库与缓存 | 仅容器内部网络访问 |
| 密钥 | 仅服务器本地保存，不进入 Git 或镜像 |

请求路径：客户端 → 主机 nginx → Sub2API 容器 → 上游模型服务。Sub2API 通过独立容器网络访问 PostgreSQL 和 Redis。

首次部署前核实服务器 CPU 架构、可用内存、磁盘、端口和现有服务，按实际容量设置三个容器的资源上限。DSH 和博客继续使用各自配置。

nginx 配置应覆盖 HTTPS、流式响应、WebSocket、长请求超时、上传限制和可信代理。修改配置后先验证，再重载。

## 6. 首次部署与升级回滚

### 6.1 首次部署

1. 确定个人代码基线与发布版本，完成构建和验证。
2. 核实服务器、域名解析、镜像拉取和资源容量。
3. 在服务器生成密码、JWT/TOTP 等密钥，初始化持久化目录。
4. 启动数据库、Redis 和应用，检查初始化与迁移日志。
5. 配置 HTTPS 和 nginx，验证管理端登录。
6. 配置一个上游账号、分组和 API Key，验证实际模型请求及计费。
7. 生成首次有效备份，演练恢复，记录运行版本。

### 6.2 后续升级

升级前检查官方迁移与二开迁移、保留旧镜像和配置，并创建可恢复的备份。首次实现采用单实例维护窗口升级，窗口中停止新的业务写入，确保数据库与应用配置备份相互一致。

应用启动会执行 SQL 迁移，见 `sub2api/backend/internal/repository/ent.go`。因此：

- 迁移向后兼容时，可以在验证后切换旧应用镜像。
- 迁移不兼容或兼容性未知时，不能宣称换回镜像即完成回滚；需要按恢复方案恢复配套数据和配置。
- 数据恢复会涉及备份时间之后的用户、订单和用量数据；应停止写入、保留故障现场，再按明确恢复目标处理。
- 第一次没有旧部署版本，验收失败应停止对外开放、保留日志和数据，再修复，不能执行不存在的版本回滚。

## 7. 验证与验收

| 层面 | 必要验证 |
| --- | --- |
| 源码融合 | 冲突已解决、二开功能仍有效、官方修复与数据迁移已核对 |
| 后端 | 现有单元测试、lint；涉及数据库/缓存时运行相应集成测试 |
| 前端 | lint、类型检查、关键 Vitest；涉及页面时进行浏览器验收 |
| 镜像 | 前端正确嵌入、版本/SHA可追踪、镜像架构与服务器一致 |
| 基础部署 | 三个服务正常、HTTPS正常、重启后数据仍存在 |
| 管理功能 | 管理员登录、上游账号、分组、Key创建和使用记录 |
| 实际网关 | 至少一个目标模型的普通请求和流式请求成功 |
| 计费 | 一次受控调用的用量、余额/订阅扣费与配置对应 |
| 恢复能力 | 备份可读取、恢复经过验证、旧镜像仍可取得 |

## 9. 建议实施顺序

1. 建立官方 remote、个人分支和版本记录规范。
2. 在 `server-ops/sub2api/` 实现部署与备份升级脚本。
3. 核实 Actions/GHCR，构建一个可追踪的个人基线镜像。
4. 完成服务器首次部署、真实请求验收和备份恢复演练。
5. 有具体需求后逐项二开，并通过相同流程发布。

步骤 1—3 可以在具体二开功能尚未确定时准备；服务器执行由用户按已交付 README 完成。
